Foreword

Why this, why now, why you

Right now, the firms experimenting with AI in plan review are almost all large: big municipal departments, national engineering outfits, software vendors selling to both. A two-principal firm running its own review-assist tool, built on its own past reports, tuned to its own jurisdictions, would be ahead of nearly everyone in the field.

That's not a stretch claim. The technology this proposal uses is the same class of tooling those large players are piloting. What they can't do is move fast. They have procurement cycles, committees, and vendors in the middle. FBE has two engineers who know exactly how a review gets done, a bounded set of codes and towns, and someone who already maintains their infrastructure. That combination is rare, and it's the whole reason a firm this size can have something working while the industry is still writing white papers.

The payoff isn't a gadget. It's throughput: more submittals reviewed per week with the same two signatures, a baseline check that never gets tired or rushed, and a written, cited trail behind every flag. Clients notice turnaround. Departments notice consistency. And when other firms eventually catch up, FBE will have years of its own review history already built into how it works.

Everything after this page is deliberately conservative: a $500 discovery day, a small pilot tested against cases you've already closed, and a stop point if it doesn't hold up. The ambition is in where this puts the firm. The plan itself takes no risks it doesn't have to.

The Bottleneck

Every submittal starts the same way, from zero

A set comes in, and the first hour or two goes to the same mechanical work every time: opening the code book, finding the sections that apply, and checking the drawings against them line by line.

That work has to happen, but it isn't the part of the job that needs a P.E. behind it. It needs someone who can read a drawing and cross-reference a standard. The judgment calls, the borderline cases, and the client conversations are where the license and the experience actually matter, and right now they're competing for the same hours as the mechanical part.

What This Is

A draft flag-list, cited, before you touch the file

Feed it a submitted plan set. It searches the actual text of the applicable code (NFPA, ICC, and the local amendments for that jurisdiction) and drafts a list of what to check and where, with the specific section cited next to each item.

The tool never issues anything. It reasons over retrieved, cited code text and doesn't memorize or improvise. No model is trained on FBE's reports, and nothing goes out the door without your signature. That's not a limitation bolted on afterward. It's the whole premise the pitch rests on.

Under the Hood

Proven parts, assembled for one firm's workflow

None of this is experimental research. Each piece is an established, commercially supported technology; the work is in wiring them together around how FBE actually reviews.

Language model API

The reading-and-reasoning engine is a commercial large language model (Claude or GPT), accessed over its API. These are the same models in production use at law firms and engineering companies for document analysis. We rent the capability per use; there's nothing to host, train, or maintain.

Retrieval index (RAG)

Rather than storing a bulk copy of NFPA and ICC text, we build a compact index of section numbers, topics, and short original summaries, plain text either of you could read yourself, closer to an annotated table of contents than a copy of the standard. When the tool evaluates a plan set, it narrows to the handful of sections actually relevant to that submittal, then cites the specific section behind each flag. That keeps every flag traceable to a real citation and keeps the tool comfortably inside normal subscriber-license terms, since it's never storing or reproducing the underlying standard in bulk.

PDF ingestion & OCR

Submittals come in as PDFs, and "already digital" doesn't mean easy: drawing sheets exported from CAD often carry a text layer whose reading order is scrambled relative to how the sheet actually reads, so pulling it as plain text produces noise, not a document. This stage routes each page correctly, clean extraction where the text is usable, a vision pass on drawing sheets, OCR for a flattened scan, so nothing in the set gets skipped or misread.

Eval harness

This is the quality-control machinery, and it's what separates a real tool from a demo. Your 8–12 past signed reports become a scored test set: every change to the pipeline gets re-run against all of them, and we measure how closely the draft flags match what you actually found. The tool has to earn its accuracy on your own closed cases before it ever touches a live one.

Storage & interface

The index and results live in Supabase, the same managed Postgres already running behind FBE's website, and any interface is built in Next.js. Because the index itself is compact, plain text rather than a bulk copy of the code, this extends infrastructure I already maintain for you rather than adding a new vendor or a heavier database than the job actually needs.

What we deliberately don't use

No model training or fine-tuning. Training a model on code text would bake it into opaque weights where it can't be cited, audited, or updated when a code edition changes. Retrieval keeps the code text external, current, and quotable, and it sidesteps the copyright questions that come with reproducing standards from memory.

What Changes

More sets through the queue, without adding headcount

  • The first pass starts from a draft, not a blank page. Review time shifts toward judgment calls instead of manual code lookup.
  • Nothing gets skipped because someone got busy. The same baseline check runs every time, on every set.
  • Every flag comes with a citation. If a client or inspector asks "where does it say that," the answer is already attached.
  • It grows with the jurisdictions you actually review. No attempt to build a nationwide code database, just the disciplines and municipalities FBE works in.
  • It already found a real pattern in your own work. The single most repeated finding in the Green Oaks letter, a door in a fire-rated corridor with no rating on the schedule, is exactly the kind of cross-sheet check this catches automatically.
  • It flags the other thing you keep writing. Structural sheets marked "Not for Construction" is a real, recurring comment, but the wording isn't consistent from firm to firm, so this checks the actual construction-readiness status rather than one fixed phrase.

What This Isn't

  • Not a black box. Every flag traces to a specific, citable code section, and the underlying index is plain text either of you could read and check yourselves, not an opaque embedding.
  • Not a replacement for engineering judgment. It drafts, you decide.
  • Not trained on FBE's reports. No fine-tuning, no model that "learns" your data. It looks things up, every time, the same way you would.
  • Not issuing anything, ever. The signature stays where it's always been.
